## Appendix — verified findings (evidence + measured numbers)

### [high] Pole IDs are read from an aspect-distorted square raster at 45° steps; deskewing in DXF space fixes 8 of 12 wrong reads

Every pole label in all four production drawings is stroke geometry, not DXF TEXT (probe: LP1709 83/83, TY1401 113/113, MN6001 1/1, BCR405 384/384 are source='stroke'), so 100% of pole IDs go through TrOCR. `_rasterise` maps x and y with two independent scale factors into a fixed 192x192 square, so a label whose bbox is 0.121 x 0.521 is stretched 4.3x along one axis before the model ever sees it. Orientation is then handled by brute-forcing 8 fixed angles 45° apart, but the labels sit at arbitrary angles (measured deskew angles on LP1709: +5, +3, -22, +32, -27, -8, -9 degrees), so no sampled angle is ever actually upright. Ironically the fix is already written in this repo: `strand_recognizer._deskew` (strand_recognizer.py:103-133) does exactly this with `cv2.minAreaRect`, and is dead code — it is defined and never called. I A/B'd it on the first 12 LP1709 pole clusters against visually-confirmed ground truth (CV8-1940, 1592, CV8-1943, CU8-1936, CV8-1944, CV8-1056, 1594, CV8-1031, CU8-1055, CU8-1054, CU8-1052, 1600): production `ocr_pole` got 4/12 right (CUB-1936, CV5-1944, CV5-1056, CV5-1065, CUB-1054, T592, T594, T600 all wrong); rotating the cluster's own segments by the minAreaRect angle in DXF space, rasterising into a 96px-tall text-line image (aspect preserved, not square) and running only 0° and 180° got 12/12 right — with 2 forward passes instead of up to 9. Note also that `ocr_pole` never receives the label's own segments: `getattr(lab, 'segments', None)` at server.py:2170 always misses because poleid.TextLabel has no `segments` field, so the whole layer is passed and filtered by a ±50%-of-bbox margin; a deskew needs the cluster's own segment list, which `poleid._build_stroke_pole_labels_from_entities` already has and discards.

**Evidence:** app_python/services/pole_ocr.py:57 (_ROTATIONS = [0,45,...,315]); app_python/services/pole_ocr.py:132-177 (_rasterise, independent x/y scale into out_px square); app_python/services/pole_ocr.py:369-468 (ocr_pole two-pass); app_python/services/strand_recognizer.py:103-133 (_deskew, never called); server.py:2170; poleid.py:563-572 (TextLabel built without segments)

**Recommendation:** Adopt it, with three changes to the prescription.

1. Plumb the cluster's own segments through. Add a field to `TextLabel` (poleid.py:9-16) and populate it at poleid.py:563-572 with the cluster's `idxs` (or the Seg objects); pass it at server.py:2170 instead of `layer_segs`. Present this as a prerequisite, not as an accuracy fix — measured cross-label contamination today is 0/83 LP1709, 2/113 TY1401, 23/384 BCR405.

2. Deskew in DXF space using the LONG side of the rect, not `strand_recognizer._deskew`. Run `cv2.minAreaRect` over the label's own segment endpoints; if `rw < rh` add 90 to the angle, then wrap into (-90, 90]. Do NOT reuse `_deskew`'s [-45,45] normalization (strand_recognizer.py:118-121): LP1709 labels return raw -10 degrees while the true baseline is 80 degrees, so that convention leaves every one of them vertical.

3. Replace the square raster with a fixed-height, variable-width render at a single uniform scale (pole_ocr.py:132-177). Height is not critical (TrOCRProcessor resizes to 384x384 regardless — verified); preserving aspect is what matters.

4. Gate the cheap path instead of deleting the sweep. Use 0/180 only when the rect is clearly elongated (long/short >= ~2.5); otherwise fall back to the existing 8-angle sweep. BCR405's clusters are single digits with 348/384 below that threshold, and the 0/180 variant turned production's '8' (conf 1.00) and '9' (0.996) into '00' and '0'.

5. Fix `_fix_pole_id` at the same time (pole_ocr.py:296-300): only apply the leading-character substitution when the cleaned raw read is NOT already valid. Without this the deskewed pipeline still reports T592/T594/T600 for labels it read as 1592/1594/1600 at confidence 1.00, and the LP1709 sample lands at 9/12 instead of 12/12.

Expected result on the verified LP1709 sample: 4/12 -> 9/12 with steps 1-4, 12/12 with step 5, using 2 forward passes instead of up to 9. Re-run TY1401 and BCR405 before merging — TY1401 (median residual 11.5 degrees, 19/113 non-elongated) should gain; BCR405 must be checked for no regression, and its real problem is that `stroke_connect_tol=0.20` splits each pole number into individual digits.

### [medium] The `_PREFIX_SUBS` "1" -> "T" rule silently corrupts correct all-numeric pole IDs

`_fix_pole_id` applies a first-character substitution table {1,l,L,I,7,| -> T} *before* checking whether the raw read is already valid, and the comment at pole_ocr.py:290-295 says this is deliberate on the grounds that those characters are "never the intended first character of a pole ID". That assumption is false for the owner's own drawings: LP1709 contains pole IDs 1592, 1594 and 1600 (visually confirmed in the rendered crops). TrOCR reads them correctly at confidence 1.00, and `_fix_pole_id` rewrites them to T592, T594, T600 because those also match `_POLEID_RE` (`[A-Z]{0,2}\d+`). The corrupted values are then `accepted=True` with confidence 0.999-1.000, so the operator never sees them flagged. That is 3 of the 12 poles I sampled — a 25% corruption rate on reads that were already right. Separately, the mid-string table at pole_ocr.py:307 omits the substitution that actually matters here: B->8. 'CUB-1936' and 'CUB-1054' fail `_is_valid` and are rejected outright, when a single B->8 candidate would recover CU8-1936 / CU8-1054.

**Evidence:** app_python/services/pole_ocr.py:261-268 (_PREFIX_SUBS); app_python/services/pole_ocr.py:281-317 (_fix_pole_id, prefix applied before validity short-circuit); app_python/services/pole_ocr.py:307 (mid_subs lacks B->8); measured: raw '1592'/'1594'/'1600' at conf 1.00 become 'T592'/'T594'/'T600', accepted

**Recommendation:** Do it, but as two cheap independent edits, and drop the unsupported severity framing.

1. (pole_ocr.py:296-304) Move the `_PREFIX_SUBS` block below the `if _is_valid(text): return text` short-circuit so an already-legal read is never rewritten. Delete the now-false docstring claim at lines 286-288. This is correctness/data-integrity hygiene — stop silently rewriting reads and marking them needs_review=False — not a measurable accuracy win on available evidence.

2. (pole_ocr.py:307) Add `"B": "8"` to `mid_subs`. Highest value-per-line item in the finding: it is the missing fourth member of the O/0, I/1, S/5 confusion set, it only fires on strings already being rejected (so it cannot corrupt an accepted read), and it targets the digit-after-prefix position where the real ID family F13-/G13-/F3-/G3- actually lives. Skip the proposed `"S": "8"` — S->5 already exists and S/8 is speculative.

3. Add a unit test over `_fix_pole_id` alone (it is pure, needs no model, and there is currently no test for it — tests/ contains only test_span_builder.py). Pin: '1592'->'1592', 'LP1709'->'LP1709', '1'->'1', 'CUB-1936'->'CU8-1936', and that a genuinely stroked-T misread still resolves. This is what makes the change safe to ship.

4. Split the drawing-wide prefix vote into its own item and re-rate its effort as medium/large. It is a real gap (server.py:2162-2201 has no cross-pole pass where strand_recognizer.py:532-567 does), and 18/115 poles currently get no read at all, so it is the item with the most headroom — but it requires restructuring the pole path to collect all reads before resolving, which is not comparable to a two-line edit.

Also worth flagging to the owner separately: 'FI5-451' shows `_POLEID_RE` is loose enough that an invalid-in-reality ID passes `_is_valid` and blocks its own correction. Tightening the regex toward the observed family (`[A-Z]{1,2}\d{1,2}-\d+`) would likely do more for pole accuracy than either substitution table, but that needs the owner to confirm the ID grammar first — the repo has no labelled ground truth to validate it against.

### [high] Confidence is averaged over `</s>` and `<pad>` steps, so the 0.60 acceptance gate is meaningless

All three TrOCR sites compute confidence as the mean of the max softmax across *every* generated step, including the EOS token and every pad step after it — steps that carry no information and score ~0.99. Measured on LP1709 poles: the correct read '1592' scores mean_all=0.897 but 0.998 over its real tokens, while the garbage read 'CO-104' scores mean_all=0.548 but 0.389 over its real tokens. The uninformative tail simultaneously drags good reads down and props bad reads up, which is why `MIN_CONF=0.60` accepted 10 of 12 LP1709 poles when only 4 were correct — every wrong answer scored ≥0.90. The per-token minimum before EOS separates the two classes cleanly on the same data: correct reads bottom out at 0.512-0.998, garbage reads at 0.136-0.181, and the minimum lands on exactly the character that is wrong ('VS' at 0.579 in 'CVS-1940'). The strand side has the mirror problem: `_MIN_CONF = 0.50` (server.py:288) is documented as a vote-share, but `_select_from` returns a raw EasyOCR CRNN score which saturates near 1.0 — on all 132 LP1709 strand candidates, zero fell below 0.50 and only 4 below 0.90, so the review gate never fires and `_post_ocr_validate`'s frequency heuristic is doing all the work.

**Evidence:** app_python/services/pole_ocr.py:244-248; app_python/services/strand_ocr.py:167-171; app_python/services/strand_recognizer.py:353-356; app_python/services/pole_ocr.py:50 (MIN_CONF=0.60); server.py:285-288 (stale comment) and server.py:1602-1633; measured on LP1709: 132/132 strand candidates ≥0.50, 4 below 0.90

**Recommendation:** Fix pole_ocr.py only; leave the other two sites alone for now.

1. In `_generate_batch` (pole_ocr.py:239-254), truncate before aggregating. Decoding is greedy and un-beamed, so `out.scores[step][b]` is already the right row and no `compute_transition_scores` rewrite is needed:

   gen_ids = out.sequences[b][1:].tolist()          # drop decoder_start
   eos = _model.config.decoder.eos_token_id
   cut = gen_ids.index(eos) if eos in gen_ids else len(gen_ids)
   probs = [float(F.softmax(step[b], dim=-1).max()) for step in out.scores[:cut]]
   conf = float(min(probs)) if probs else 0.0

   Return the min, not the mean: the audit's own data shows the minimum lands on exactly the wrong character ('VS' at 0.579 in 'CVS-1940'), and an ID is only correct if every character is. Guard `cut == 0` (empty read) to 0.0 so a model that emits EOS immediately cannot score high.

2. Re-tune both thresholds together, not just MIN_CONF. `FAST_CONF_THRESHOLD = 0.95` (pole_ocr.py:324) is the more damaging of the two - it skips the whole 8-angle sweep, so an inflated pass-1 read stops the pipeline from ever gathering the evidence that would correct it. On the new min-token scale 0.95 is a much stricter bar and will send more poles to the sweep; that is the intent, but measure the added latency, since the sweep is 8 forward passes.

3. Treat this as a selection change and regression-test it. `_pick_best` (pole_ocr.py:360) ranks rotations by this same score; in my run the correct read beat a wrong one by 0.001 under the current metric. Before/after per-pole reads on LP1709 will show whether ranking improved, and that check is more informative than the accept-rate number.

4. Build the label set first - it is the blocker. There are no OCR ground-truth fixtures in tests/. Hand-label the pole IDs on the four drawings in uploads/ (LP1709, TY1401, MN6001, BCR405) as a JSON fixture and add a test that reports read accuracy plus the accepted/correct confusion matrix. Without it, any threshold is guesswork, and this fixture is a prerequisite for every other accuracy change the owner will want.

5. Strand side - do the cheap half only. Correct the stale comment at server.py:285-288 to say what `_select_from` actually returns (a raw EasyOCR CRNN max, discounted 0.85 when the value was seen once - strand_recognizer.py:408-409); a comment that misdescribes the scale is how a dead gate survives review. Do NOT rewrite `_AGREE_W`. If you want an agreement-based review gate, add it as a separate signal - flag when the winning value was seen at only one sweep angle, i.e. `count[best] == 1`, which `_select_from` already computes - and leave the 0.05 selection weight alone, since its rationale at strand_recognizer.py:364-367 (wrong-orientation reads must not out-accumulate the correct upright read) is about picking the answer, not about gating it. Note that strand_recognizer.py:447 re-sweeps whenever confidence < 0.60, which inflates the reported number and is part of why the 0.50 gate never fires.

6. Delete strand_ocr.py or mark it unused. It is imported nowhere (only README.md:83 and a requirements.txt:29 comment reference it). Leaving a second, differently-tuned copy of the same confidence bug in the tree guarantees someone re-introduces it.

### [high] The precompute path, which runs on every upload, never calls the pole OCR at all

`_run_precompute` is enqueued on every file upload and is what populates the persisted Supabase session. It builds pole entries directly from `_poleid.find_pole_labels` and sets `name = _poleid.clean_label(lab.text)`. That alone stops the persisted session from claiming 384/83/113 unread poles are confirmed, and makes the restored view (Polepanel.tsx:453/582, page.tsx:276) show them as pending instead of accepted.

STEP 1b (same edit, one more line). page.tsx:315 sets poleDone: full.poles.length > 0, which makes Polelayout.tsx:198-209 mount as scanStatus="done". Gate that on at least one pole not needing review, otherwise the restored UI still reads as a finished scan.

### [high] Pole clustering uses a fixed absolute tolerance while the strand path is scale-adaptive — MN6001 yields 1 pole instead of ~23

`POLE_CONFIG.stroke_connect_tol` is hardcoded at 0.20 drawing units and passed to `poleid._cluster_segments`. The strand pipeline solved this problem: it derives every distance threshold from `CONNECT_TOL * estimate_scale(all_segments)` per drawing (with an explicit comment saying so). The pole path never got the same treatment. Measured across the four production drawings: on uploads/MN6001.dxf the pole layer's 138 LWPOLYLINEs flatten to 728 segments which, at tol=0.20, collapse into a *single* connected cluster — so the drawing reports 1 pole label while the same layer carries 23 CIRCLE pole symbols. LP1709 (83 clusters), TY1401 (113) and BCR405 (384) happen to sit at a compatible scale, which is why this has not been noticed. Nothing downstream can recover from it — the model is never shown the missing labels.

**Evidence:** server.py:2006 (stroke_connect_tol=0.20); poleid.py:526 (_cluster_segments(segments, tol=config.stroke_connect_tol)); server.py:1667-1674 (strand path: scale = estimate_scale(...); tol = CONNECT_TOL * scale); measured: MN6001 PDF_s48$POLE -> 728 segments -> 1 cluster, 23 CIRCLEs on the same layer

**Recommendation:** Make the pole path scale-adaptive the same way the strand path already is, with four amendments to the original proposal.

1. Use the strand path's existing reference constant, applied to the pole layer's own segments: scale = median(pole layer segment lengths) / REF_MEDIAN_SEGLEN (server.py:153, value 0.0125), then build a per-drawing PoleIdConfig with stroke_connect_tol = 0.20 * scale. Do not invent a new reference. Measured: MN6001 1 -> 22 labels, LP1709 83 -> 83 (unchanged), TY1401 113 -> 116.

2. Scale the distance-valued floors by the same factor — mandatory, not optional. stroke_min_total_length (0.30) and stroke_min_bbox_w/h (0.05) at poleid.py:539-543 must be multiplied by scale; scaling the tolerance alone yields ZERO labels on MN6001 because its real clusters total ~0.07 in length with a ~0.017 bbox. Leave stroke_min_segments (4) and stroke_max_endpoints (24) alone — they are counts, not distances. _endpoint_count at poleid.py:551 reuses the same tol, so it follows automatically.

3. Clamp the derived scale. BCR405's pole layer has median segment 0.165 -> scale 13.2 -> tol 2.64, roughly twice its glyph height, which merges adjacent pole codes and drops BCR405 from 384 to 328 labels. Cap the tolerance at about one median cluster height (or clamp scale to roughly [0.05, 2.0]) and confirm BCR405 stays at 384.

4. Fix the precompute path too, not only the interactive one. server.py:3029-3049 (_run_precompute) builds poles with no _untagged_pole_circles rescue and no OCR call, and writes needs_review=False — so MN6001 persists to Supabase as a single pole literally named POLE_000. The interactive path at server.py:2224 at least recovers the 23 circle positions as UNTAGGED-xxx.

5. Write the regression test with pinned per-drawing counts (LP1709 83, TY1401 113, BCR405 384, MN6001 >= 20), not by comparing to the CIRCLE count. The circle-count heuristic only holds on MN6001: TY1401 has 113 labels against 35 circles, and BCR405 has no circles at all.

### [low] The advertised EasyOCR+TrOCR ensemble does not exist, and its weighting constants are dead code

`predict_with_easyocr`'s docstring promises a "dual-engine ensemble EasyOCR+TrOCR" and the startup banner prints "Pre-warming strand recognizer (EasyOCR + TrOCR)", but `USE_TROCR_DEFAULT` reads STRAND_USE_TROCR which defaults to '0', so only EasyOCR ever runs. Worse, the machinery meant to combine them was never wired: `_EASYOCR_WEIGHT`, `_TROCR_WEIGHT`, `_AGREEMENT_BONUS` and `_SEG_BONUS` each appear exactly once in the file — their own definition — and `_select_from` simply takes the maximum raw confidence across all reads regardless of which engine produced it. Since TrOCR's mean-token-probability sits near 0.95 even when wrong (see the confidence finding) while EasyOCR's CRNN score is a different scale entirely, turning the flag on today lets TrOCR outvote EasyOCR by construction. I measured it: enabling TrOCR on the 4 lowest-confidence LP1709 strand crops flipped one read from '21' to '22' (the crop is '27' — both wrong) while *raising* its reported confidence from 0.85 to 0.95, and cost 11 s/crop versus 0.29 s. Two of the four gained confidence without changing value. There is no measured case where it corrected an error. The remote-GPU escape hatch is dead too: `REMOTE_TROCR_URL` is read in exactly one place, to skip prewarm — no client ever posts to colab/server.py.

**Evidence:** server.py:379-386 (docstring) and server.py:4963; app_python/services/strand_recognizer.py:68 (USE_TROCR_DEFAULT); app_python/services/strand_recognizer.py:54-56 and :268 (weights defined, never read); app_python/services/strand_recognizer.py:378-409 (_select_from takes max conf only); server.py:4972 (sole REMOTE_TROCR_URL reference); measured: 4 unsure LP1709 crops, 45.1s with TrOCR, 1 value changed wrong->wrong

**Recommendation:** Take the deletion branch only. Do not build the calibrated ensemble.

### [medium] Everything runs unbatched; strand_recognizer hardcodes gpu=False on a CUDA machine and loads a second EasyOCR reader

`strand_recognizer._load_easyocr` constructs `easyocr.Reader(["en"], gpu=False)` unconditionally, while server.py's own loader correctly picks the device from `torch.cuda.is_available()` — which returns True on this machine (torch 2.9.1+cu128). Both readers are loaded at startup, so two copies of EasyOCR sit in memory and the accuracy-critical one runs on CPU. `gpu=False` also silently triggers EasyOCR's `quantize=True` default (int8 dynamic quantization of the recognition CRNN), a precision change nobody chose. ### [low] render_crop stretches every digit: x and y are scaled independently to fill a square
